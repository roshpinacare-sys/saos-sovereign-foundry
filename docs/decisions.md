## D1 — פורט הקרנל מ-CJS ל-TypeScript במקום להריץ את הקוד ההיסטורי כמו שהוא

- **מה**: `sovereign/core/kernel.cjs` מארכיון steem-main נכתב מחדש כ-`src/lib/saos/kernel.ts` (ועמו canonical-json, merkle, evidence).

- **תועלת**: בדיקות-זמן-ריצה, שילוב UI/API מיידי, אין גבול בין שכבות.
- **מאישור**: המשתמש (הנחיה "להקים מחדש ברמה גבוהה הרבה יותר") — worklog Task 2.

## D11 — אטומיות פעימה: טרנזקציה + write-lock + retry + idempotency (Task 4)

- **מה**: POST /seal מריץ את כל הכתיבות (height, seal, leaves, anchors, receipt, oplog) בתוך טרנזקציית Prisma אחת, מאחורי `withWriteLock` (mutex בתהליך), עטוף ב-`retryWrite` (backoff על P2002 + תקלות-נעילה חולפות); `batchId` מזריע את כל ה-nonces ומשמש מפתח-idempotency (root זהה → מוחזר החותם הקיים).
- **למה**: F1/F2 נסגרו רק בשילוב כל השכבות — הטרנזקציה נותנת אטומיות, ה-mutex מונע תחרות על נעילת SQLite, ה-retry מכסה ריבוי-worker, ה-idempotency מונע כפילויות ומאפשר לקוח בטוח-לניסיון-חוזר.
- **חלופות**: (א) AUTOINCREMENT/sequence ב-SQLite — נדחה: דורש שינוי-סכימה עמוק ולא פותר root-collision; (ב) SELECT ... FOR UPDATE — לא קיים ב-SQLite; (ג) Postgres מיידי — נדחה: חורג מסביבת הסנדבוקס.
- **סיכון**: ה-mutex הוא בתהליך — ריבוי-תהליכים דורש Postgres (מתועד F5); idempotency לפי root: batchId עם stamps שונה = root אחר (מתועד).
- **תועלת**: הוכחה חיה 8/8 פעימות מקבילות, heights 1..N רציפים, אפס 500-ים.
- **מאישור**: הנחיית המשתמש (משימה 1 ב-Task 4).

## D13 — שחזור `at` מוכח-דיג'סט + אימות DAG במקום שכתוב היסטוריה (Task 4)

- **מה**: עמודה `at` ל-EvidenceReceipt; backfill חד-פעמי שמשחזר את זמן-החיתום ההיסטורי רק כשה-sha256 מוכיח אותו (41/41); אימות השרשרת עבר ל-`verifyChainDag` — כל prevDigest חייב להיות digest של קבלה קודמת, פיצולים מדווחים ולא נשכתבים.
- **למה**: השרשרת ההיסטורית הייתה בלתי-ניתנת-לאימות (BUG-004) והכילה פיצול אמיתי (BUG-005). שכתוב prevDigest/digest = זיוף ראיות — נאסר. שחזור ע"י הוכחת-האש אינו זיוף: הדיג'סט הוא המקור.
- **חלופות**: (א) להתעלם מההיסטוריה ולהתחיל שרשרת חדשה — נדחה: אובדן ראיות; (ב) לתקן את הפיצול בכוח — נדחה: זיוף.
- **סיכון**: `forks:[17]` נשאר בפלט לנצח — מכוון (עדות אמיתית).
- **תועלת**: השרשרת כולה מאומתת; ההיסטוריה שלמה וכנה.
- **מאישור**: עיקרון הכנות (חוקי ברזל 2).

## D15 — שכבת הרשאות: hash בלבד + cookie חתום (Task 5)

- **מה**: `SAOS_ADMIN_KEY_HASH` (sha256-hex) בלבד על השרת; התחברות → cookie `saos_session` חתום HMAC (HttpOnly, SameSite=Strict, 12h); חלופה `Authorization: Bearer`. fail-closed: בלי hash — 403 לכל פעולה רגישה.
- **למה**: אפס סודות בקוד/DB/לוגים; סוד לא-מוגדר חייב להתנהג כסגור, לא כפתוח.
- **חלופות**: NextAuth מלא — נדחה (overkill לאופרטור-יחיד); JWT stateless עם secret בקוד — נדחה (סוד בריפו אסור).
- **סיכון**: אין revocation גלובלי (סיבוב secret = תלול); מפתח חלש ניתן לניחוש — הגבלה 8/דק' + הנחיה למפתח ארוך.
- **תועלת**: השער הראשון מפני הפעלת פעולות-רגישות ע"י אנונימיים.
- **מאישור**: הנחיית משתמש Task 5 מיסיון 1.

## D17 — ממשק חתימה keyless: המערכת מייצרת, האדם חותם, חוזר רק txid

- **מה**: PendingSignature ללא שדה-מפתח כלל; SignRequest = payload+payloadHash+digestToSign+metadata+הוראות; PATCH מקבל txid ציבורי בלבד, בלתי-הפיך; רישום-כפול נדחה.
- **למה**: חוק-זהב — פעולה שדורשת מפתח פרטי לא מבוצעת/נשמרת/מודפסת; ההגנה מבנית (אין עמודה), לא נוהלית.
- **חלופות**: keystore מוצפן בשרת — נדחה מיידית; חתימה בתוך הסנדבוקס — נדחה (סותר את עקרון-הכנות ואת ההנחיות).
- **סיכון**: תלות במשמעת-אופרטור מחוץ למערכת; אין ולידציה קריפטוגרפית שה-txid אכן עוגן את ה-digest (העגינה הציבורית עצמה תאמת).
- **תועלת**: הדרך היחידה שבה עוגנים אמיתיים יכולים לקרות **בלי** שמפתח חי ייגע בסוכן/ריפו/שרת.
- **מאישור**: הנחיית משתמש Task 5 מיסיון 4 + הערה-קריטית בהודעה.

## D19 — גיבוי באמצעות `VACUUM INTO` + אימות-חובה, restore ללא-אימות = אסור
